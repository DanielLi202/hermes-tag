## 0. 结论

### 0.1 下架原因（事实，不是猜测）

不只是"长期未维护"。具体是 **catalog 规则 9（No runtime overrides of Hermes core）**：

- 2026-09-15 维护者 sweep 把 hermes-tag 收录进 `plugin-catalog/`（commit `5d59366010`，pin `250785b9`）。
- 2026-10-01 teknium1 在本仓库开 **issue #26**（仍 OPEN），只点名**一处**违规：
  `src/hermes_tag/__init__.py:76` 原地替换 `hermes_cli.commands.slack_native_slashes`。
  给出的修法：用 `ctx.register_command(...)`；需要 Slack 原生 slash 槽位就去上游提 seam issue。
- 2026-10-03 commit `b71ba34819` 一次下架 11 个插件（hermes-tag 在列）。**这是普通下架，没有进
  `removed.yaml`**：已装用户继续可用，修好后提一个新 PR 加回 `plugin-catalog/hermes-tag.yaml` 即可回来。

"subclass 内置 adapter + 用同名 `register_platform` 覆盖"这一架构**是被允许的**。
`gateway/platform_registry.py:181-183`（`core_ships_platform` docstring）明确写了
"A user plugin may replace such an adapter"。所以要删的只有那一个函数。

### 0.2 价值判断：仍有价值，飞书最明显；护城河从"能缓冲"收窄为"选得准 + 隐私"

| 能力 | v0.22.5 飞书原生 | v0.22.5 Slack 原生 | hermes-tag |
| --- | --- | --- | --- |
| 未 @ 群消息缓冲为上下文 | 无（仅 `require_mention` 门禁）；`observe_unmentioned_group_messages` **只对 Telegram**（`gateway/config_loader.py:218`） | 线程内 hydration（`plugins/platforms/slack/adapter.py:4335`） | Tier-0，按 chat 白名单 |
| 晚 @ 时带回早先图片原图 | 无 | 仅"线程根消息图片、首次线程内 @"（同上 `:4349-4369`） | `deictic_recent` / `focused_reply` / `thread`，有界 |
| 有界证据选择（命名 scope） | 无 | 无（线程全量/增量回灌） | `ContextSelector` |
| 按 chat 隔离的长期记忆 | 无（只有 `group_sessions_per_user`） | 无 | Tier-1，仅 @ 产生，tombstone |
| 脱敏审计 / 按 chat 清除 | 无 | 无 | `/tag admin audit|clear|disable` |

依据：飞书官方文档页（hermes-agent.nousresearch.com/docs/user-guide/messaging/feishu）+ 对 v0.22.5 的
`gateway/` 和 `plugins/platforms/{feishu,slack}` 做的 grep。

需要正视的三点：

1. **机制已被上游背书**：v0.22.x 新增公开 hook `pre_gateway_dispatch`。官方文档
   （`website/docs/user-guide/features/hooks.md:1290-1360`）给出的用例就是
   "Listen-only group chats (only respond when tagged; buffer ambient messages into context)"。
   所以光会"缓冲"已经不算差异点。差异点只剩**选择质量**（命名 scope、多模态原图、有界预算）和
   **按 chat 的隐私/审计**。
2. **Slack 价值被部分覆盖**：线程场景原生已能回灌上下文和根消息图片。hermes-tag 在 Slack 剩下的
   价值是：频道级（非线程）晚 @、deictic 指代、Tier-1 记忆、审计。
3. **Telegram 原生已有扁平的 observed group context**。`docs/design/0.5.0-telegram-plan.md` 的竞争前提
   需要按 v0.22 重新核对（见 §5）。

另外有一项直接价值：时令 PM 生产 bot 依赖本插件。它现在跑在 Hermes v0.17.0 上不受影响（memory 记录，
2026-07-09），但**一旦升级 Hermes 就会坏**（见 §1）。

### 0.3 结论

值得做，范围是**兼容修复 + 重新上架**，不是重写。验收标准是**重新进入 catalog**，同时在 v0.22.5 上
通过 AGENTS.md §4 的四项实测。

## 1. 已确认的断点（v0.22.5 静态证据）

- **B1 规则 9 违规（下架直接原因）。** `src/hermes_tag/__init__.py:35-76` 的
  `_ensure_slack_native_tag_command` 原地替换了 core 模块属性，`hermes plugins validate` 的
  `no core override` 检查（`hermes_cli/plugin_validate_core_override.py`）会拒收。
- **B2 硬断：飞书每条入站消息都会抛异常。** 上游 `_extract_message_content` 现在返回 **6 元组**，新增了
  `media_text_inlined: list[bool]`（`plugins/platforms/feishu/adapter.py:3007-3031`，调用点 `:2618`）。
  在 pin 版本（`gateway/platforms/feishu.py:3602`）它是 5 元组。我们的覆盖
  `src/hermes_tag/platforms/feishu.py:176` 按 5 个解包，会抛 `ValueError`。`adapter_factory` 的兜底只管
  构造阶段，接不住这里。
- **B3 注册参数漂移（实测后下调：凭据能解析，但丢了 home channel 和依赖懒装）。** 我们手抄的
  `register_platform` 参数（`platforms/feishu.py:271-290`、`slack.py:251`、`dingtalk.py:207`）缺了上游的
  `env_overrides` / `env_enable_credentials`、`ensure_deps_fn`、`SEND_ENTRY_KWARGS`、`DASHBOARD_CARD`、
  `platform_hint`、`display_tier`。覆盖插件注册同名 entry 后，`_bundled_env_fallbacks`
  （`gateway/config_env.py:244-261`）会跳过这个平台，env 桥接不跑。Phase 0 实测（§1.2 #9/#10）：
  - **凭据不受影响。** adapter 自己通过 `_extra_or_secret("app_id", "FEISHU_APP_ID")`（`adapter.py:1393`）从
    secret 兜底，`_app_id` 能解析。原先"飞书大概率连不上"的判断是错的。
  - **`FEISHU_HOME_CHANNEL` 丢失。** 插件启用时 `home_channel=None`，禁用时为 `oc_...`。依赖 home channel 的
    cron 和通知投递会失效。
  - **`check_fn` 用错了函数。** 它指向我们的 `check_requirements`，后者调用上游的 `check_feishu_requirements`，
    而这个函数现在是**主动安装器**（`adapter.py:1231-1242`）。#79812 明确禁止把它当 `check_fn`：状态展示会
    顺带触发 pip 安装。`ensure_deps_fn` 为 None。
  - **三个平台都一样**：飞书、Slack、钉钉的 entry 都是 `env_overrides=False`、`ensure_deps_fn=None`。
  - `SEND_ENTRY_KWARGS` 缺失对 send_message 目标解析的影响没有单独实测。
- **B4 漂移没被发现的根因：CI 是瞎的。** CI 只跑 stub，stub 写死的是旧的 5 元组契约。
  `tests/test_real_hermes_compat.py` 把 `/Users/february/.hermes/hermes-agent` 写死在路径里，CI 上永远
  self-skip。实测（§1.2 #6-#8）：在装了 v0.22.5 的 venv 里跑全套，结果与 CI 模式一样（124 通过、1 跳过）。
  把 compat 测试指向 v0.22.5 也能通过，因为它只检查注册 key，看不到 B2/B3。
- **B5 硬断：`pyproject.toml` 的 `hermes` extra 导致装上后无法启用（Phase 0 新发现）。** 这个 extra 声明了
  `hermes-agent[feishu,cron] @ git+...@v2026.6.19`。v0.22.5 的包管理器会把插件放进一个以 hermes-agent 为成员的
  uv workspace 做依赖解析，遇到这个条目直接失败：
  `` `hermes-agent` is included as a workspace member, but is missing an entry in `tool.uv.sources` ``。
  后果：
  - `hermes plugins install … --enable` 输出 `✗ Enable 'hermes-tag' refused`，插件停在"已安装、已禁用"。
  - catalog CI 门禁 `validate --install-deps` 的依赖准备也失败。
  - 对照实验：只删掉这个 extra、其余不变，就能安装并启用。

  复现环境是 dev checkout 安装的 v0.22.5，正式安装器装的 Hermes 尚未验证。
- **B6 安装扫描判 caution，非交互安装被拦（Phase 0 新发现）。** 安装期安全扫描（`tools/plugin_guard.py`）
  对 main 报 27 条 finding。判定由最高严重度决定：HIGH 判 caution，只有 MEDIUM/LOW 判 safe
  （`tools/skills_guard.py:949-952`）。唯一的 HIGH 是 `after-install.md:247` 文档示例里的 `__import__("os")`
  （类别 obfuscation）。caution 的后果：
  - 非交互安装（AGENTS.md 的 agent 安装路径）结果是 `Decision: BLOCKED`；
  - 交互安装需要用户逐次确认；
  - 只有 catalog 的 reviewed pin 会自动放行（`hermes_cli/plugins_cmd.py:205-206`）。

  对照：把那一行改成 `import os` + `os.path.expanduser(p)`，判定变为 `safe`（剩 26 条，全是 MEDIUM/LOW）。
- **B7 增强后的事件丢掉上游字段（D5 评审发现，已核实）。** 启用会话的路径是 `_dispatch_inbound_event` →
  `TagEngine.handle_message` → `_enhance_event`（`base.py:300`）→ `_copy_event`（`base.py:738-760`）。
  `_copy_event` 只拷贝 10 个字段重建事件，v0.22.5 `MessageEvent`（`gateway/platforms/event.py:44-113`）的其余字段
  全部回到默认值，其中有：
  - `media_text_inlined`：消费方 `gateway/run_inbound.py:1534-1549` 用 `inline_flag is not False` 判断"已内联"，
    所以空列表会让模型以为 csv/json/超限等**未内联**的文本文档"正文已在下方"，从而不去读缓存文件；
  - `channel_prompt`（`gateway/run_turn.py:261-272` 消费）、`auto_skill`（Slack `adapter.py:4736-4743` 写入）：
    频道 prompt 和频道绑定 skill 在启用会话里失效；
  - `metadata`、`reply_expected` 等。

  `core.py:501` 已经有一个保留全部 dataclass 字段的 `copy_event`，`_copy_event` 是一份有损的重复实现。
  stub `MessageEvent`（`platforms/feishu.py:74-84`）没有 `media_text_inlined`，所以现有测试看不到这个问题。

### 1.1 风险（Phase 0 已实测 R1/R3/R5；R2 尚未实测）

- **R1 模块双身份。** 上游 loader 以 `hermes_plugins.<slug>` 名义导入 bundled 平台
  （`hermes_cli/plugins_loader.py:699-760`，延迟加载），而我们导入的是
  `plugins.platforms.feishu.adapter`。如果两份模块都加载了，类身份和模块级懒加载状态（`FEISHU_AVAILABLE`、
  `lark`、去重缓存）会各有一份。
  **实测未复现**（§1.2 #9/#10）：
  - 插件启用时，`sys.modules` 里只有一份 `plugins.platforms.feishu.adapter`，我们 adapter 的基类就是它；
  - 插件禁用时，bundled 模块以 `hermes_plugins.platforms__feishu.adapter` 的名字加载。

  这次只覆盖了配置加载和 adapter 构造两条路径。gateway 长时间运行后，cron 投递或 standalone send 会不会
  懒加载出第二份模块，留到 Phase 2 再看。

## 2. v0.5.0 范围

实现方按 CLAUDE.md 默认交 Codex，本文即 spec；Claude 负责评审和验收。

**M1 删除 Slack 猴补丁（B1）。** 删掉 `_ensure_slack_native_tag_command`、`register()` 里对它的调用，以及
`tests/test_slack_native_patch.py`，保留现有的 `ctx.register_command("tag", ...)`。
在 `docs/known-limits.md` 记一条：命令总数超过 Slack 50 条上限时，原生 `/tag` slash 可能被截掉，
这时改用频道内的 `@bot /tag ...`（走 `handle_message`，不受影响）。
*验收：* 运行时代码里不再出现对任何 core 模块属性的赋值；`hermes plugins validate` 的
`no core override` 检查通过。

**M2 适配 6 元组，增强事件保留上游字段（B2、B7）。**
- `FeishuTagAdapter._extract_message_content` 原样透传上游返回的 `media_text_inlined`，只改 `text`。
- 删除 `base.py` 的 `_copy_event`（连同 `base.py:840` 的 `__all__` 条目和 `adapter.py:14` 的 re-export），
  `_enhance_event` / `_command_event` 改用 `core.copy_event`。
- `core.copy_event` 现在的写法在真实 `MessageEvent` 上同样会失败：它用 `fields()` 收集全部字段再调用 `cls(**values)`，
  而 v0.22.5 有 `init=False` 字段（`event.py:116,118`）。实测报错
  `TypeError: MessageEvent.__init__() got an unexpected keyword argument '_gateway_accepted'`。
  改为 `copy.copy(event)`，再对可变容器（`media_urls`、`media_types`、`media_text_inlined`、`metadata`）各做一份新拷贝。
- `_enhance_event` 往 `media_urls` 末尾追加 parent/related media 时，`media_text_inlined` 要同步对齐：
